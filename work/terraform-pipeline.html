CI/CD / Infrastructure as code

Terraform delivery pipeline

How infrastructure changes reach many AWS accounts: one root per account, a plan on every pull request, and a gated apply on merge.

Layout

Figure 1. Change to applied

One repository, one Terraform root per account (and per application stack). A root is any directory with a backend.tf. The pipeline finds roots itself, so adding a stack needs no workflow change. Each account has its own state, its own CI role and its own environment.

End to end

Plan on pull request

  1. Discover. Diff against the base, walk each changed file up to its nearest backend.tf. The unique roots become the plan matrix.
  2. Plan per root, in parallel. The CI role is picked per root, assumed by OIDC, then init and plan.
  3. Mid-import guard. While a root still has a live import block, the plan must show 0 to change and 0 to destroy, or the check fails. That proves an import changed nothing.
  4. Out-of-band guard (warn only). A resource added to code that is already in state, with no import block, probably came from a manual import. The PR gets a comment, never a failure.
  5. Comment. The plan is posted on the PR for a human to read.

Apply on merge

  • Approval gate. Each apply job runs in an environment named after the account, with a required reviewer and branch restrictions. Nothing reaches AWS unattended.
  • One root at a time. max-parallel: 1 plus a non-cancelling concurrency group, so state locks never collide.
  • -auto-approve is acceptable only because the plan was reviewed on the PR and the environment approval sits in front.

CI roles and grants

Figure 2. Read by default, write by feature grant, cannot edit itself

  • CI starts with read access for planning and write access to state. Write access to resources comes from separate managed policies, one per application stack, each scoped to what it needs.
  • CI cannot grant itself access. An explicit deny blocks changes to its own policies. A grant is applied once by hand with admin credentials and a -target; after that CI applies everything else.
  • Managed policies, not inline, because inline policies share a size cap.

Importing existing resources

  1. Write config to match the live resource and add an import block.
  2. Open a PR. CI enforces 0 changes, 0 destroys. A diff means the code does not describe reality yet.
  3. Merge. Apply records it in state.
  4. Remove the import block in a later change.
An import block whose resource config is missing breaks every later apply in that root. Merge the two together or not at all. Re-running a failed run replays its original commit, so check the SHA first.
